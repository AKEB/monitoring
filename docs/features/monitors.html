Monitors

Monitors are the checks (or folders) that define what Monitoring watches and how it alerts.

Organization

  • Folders — hierarchy; ACL and maintenance inherit to children
  • Enable/disable per monitor; copy monitor in admin UI
  • Assign workers and notify channels (ACL-filtered)
  • Fail modes: notify when any / majority (≥50%) / all assigned workers fail
  • Interval, timeout, re-alert cadence; optional signatures; api_enabled for Status API

Custom error text via Log

HTTPS, HTTP JSON and External can attach a human-readable message that appears in events and notifications as Log: ….

HTTPS / HTTP JSON (checked resource → worker)

The endpoint under check returns an optional response header named exactly Log. The worker copies it into response_error (prefixed with Log: , sanitized, truncated). If present, it overrides other response_error text for that check (including HTTP JSON messages). The server stores it on the monitor as external_log on FAIL and uses it in fail alerts.

HTTP/1.1 500 Internal Server Error
Log: upstream timeout on payment-api

External (callback → server)

On GET /api/external/{hash}/?status=ok|fail (also accepts synonyms like error/down/0 for fail), pass custom text with priority:

  1. HTTP request header Log
  2. Query ?log=…
  3. Query ?message=… (alias)
# Header
curl -H 'Log: disk full on backup' \
  'https://monitoring.example.com/api/external/<64hex>/?status=fail'

# Query parameter
curl 'https://monitoring.example.com/api/external/<64hex>/?status=fail&log=disk%20full'

Without custom text, fail alerts use a default like External status: fail. The last log is kept for heartbeat-style re-alerts.
