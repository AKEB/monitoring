Architecture

Monitoring is a control plane (Server) plus two kinds of edge processes: Workers that pull check jobs, and Agents that push host telemetry.

Components

ComponentImage / binaryRole
Serverakeb/monitoringUI, MySQL, Memcached, scheduling, ACL, alerts, APIs
Workerakeb/monitoring-worker-goExecutes HTTP/TCP/Ping/Docker/exporter jobs; protocol 2.0+
Agentakeb/monitoring-agentReports CPU/RAM/disk/net/listeners/Docker/Proxmox/auth every ~30s

Data flow

sequenceDiagram participant UI as Web_UI participant S as Server participant W as Worker participant A as Agent participant N as Notify UI->>S: Configure monitors and ACL W->>S: get jobs protocol 2.0 S-->>W: job list W->>W: Run checks W->>S: state results A->>S: report host metrics S->>S: Evaluate status events S->>N: Alert when thresholds fail UI->>S: Live dashboard via WebSocket

Storage

  • MySQL — configuration, events, aggregated metrics
  • Memcached — short-lived caches (e.g. status API)
  • Raw check logs are aggregated; old detail is pruned (about 24h)

Why workers and agents are separate

Workers answer “is the service reachable from this network?”. Agents answer “what is happening on this machine?”. You can run many workers worldwide and many agents on private hosts without opening inbound ports to the Server.
